# 路径引导MPC方案——全面评测分析报告

## 一、执行概要

当前MPC求解器**未能稳定产生可行解**。最近一次运行结果：Z=280（仅W1工作4天），Day 34在(21,21)耗尽燃油失败，未到达终点(30,15)。成功率约20%（多次调参中仅少数成功）。

以下是基于算法原理、实现细节和多次调试日志的系统性评测。

## 二、正确性分析

### 2.1 全局路径规划

**当前实现**：
```python
cost = d_from + WORK_MAX_CONSECUTIVE[wn] * 4
score = benefit / (cost + 0.01)
```

按分降序得到路径。本轮输出：`[(1,15), (6,21), (24,24), (15,9), (30,15)]`。

**问题1：d_to（到终点距离）未纳入cost**

`plan_global_path()` 中计算了 `d_to` 但从未使用。这导致：
- W3(24,24): d_from=32, cost=44, score=84/44=1.91
- W2(15,9): d_from=20, cost=40, score=75/40=1.88

W3略高于W2，路径成为 W1→W3→W2。但从W1(6,21)到W3(24,24)需要行走18+3=21格，到W2(15,9)只需9+12=21格——距离相同。关键是从W3再到W2还需21格。如果路径是W1→W2→END，从W2到END只需15+6=21格；而W1→W3→W2→END多了W3→W2的21格绕路。

**修正**：cost应包含 `d_from + d_to + work_days * avg_work_consume`，或使用旅行商(TSP)式全局优化。

**问题2：贪心排序≠全局最优**

三个作业点的访问顺序是排列问题（3!=6种）。贪心按score排序不保证全局最优。正确做法是枚举6种顺序，对每种计算期望Z增量和总旅行成本，选最优。

**问题3：d_from始终从START计算**

第二个作业点的d_from应该从上一个作业点计算，而非从START。当前代码对所有作业点统一使用`abs(START[0]-wp[0])+abs(START[1]-wp[1])`，这在物理上毫无意义——船不会每次都从START出发去下一个点。

### 2.2 每日MPC决策

**当前逻辑**：
```
if 到达目标:
    if 是作业点且可作业 → 作业
    else → 推进到下一目标
if 在补给点且资源低 → 补给
else → 向目标移动一步
if 雷暴且移动后资源<15 → 停泊
```

**问题4：作业点离开后无资源检查**

船在W1工作4天后离开，燃油从49降至约30。前往W3需21步移动（期望消耗约21×8=168资源），30燃油显然不够。但MPC决策中，目标已设为W3，`move_towards`只会向W3移动，直到O耗尽。缺少"目标不可达时重新规划"的机制。

**问题5：补给触发过于保守**

补给条件为`load<40%`或`O<30`。以初始load=350、CAP=400计算，40%即load<160才补给。船在W1工作后load约200，经过补给点S1时不触发补给。但后续到W3还有21格（需要约168资源），200-168=32勉强够但风险极高。补给门限应考虑**未来路径的期望资源需求**，而非仅看当前存量。

**问题6：风暴避险阈值不区分资源类型**

雷暴日`O-eO<15 or H-eH<15 or F-eF<15`则停泊。三种资源的消耗比例不同（移动时O=8, H=4, F=3），用相同阈值15不合理。且15的阈值偏高——每遇雷暴就停泊相当于浪费一天。

### 2.3 环境步进

**问题7：work_days在移动时被全局重置**

```python
if a.startswith("move_"):
    for wn in WORK:
        if (ns.x, ns.y) != WORK[wn]:
            ns.work_days[wn] = 0
```

任何移动都重置所有不在目标位置的作业点计数。这意味着如果船途经W1（比如从START去W3路过(6,15)附近但不精确到(6,21)），它不会重置W1计数。但如果恰好经过(6,21)再离开，W1计数归零，可以重新作业。这个行为是否合理值得商榷——题目中"单次最多连续作业"的含义是每次访问最多连续N天，离开后重访应可重新计数。当前实现正确但不够清晰。

## 三、全局最优性分析

### 3.1 最优性缺失的根源

| 层面 | 是否最优 | 原因 |
|------|---------|------|
| 工作点访问顺序 | ❌ 贪心非最优 | 未枚举全排列，cost未含d_to |
| 单点工作天数 | ✅ 最优 | 总是工作到上限（4/5/3天） |
| 补给时机和数量 | ❌ 启发式 | 基于当前load的硬阈值，非前瞻优化 |
| 路径选择（点间移动）| ✅ 最优 | 曼哈顿最短路径 |
| 风暴应对 | ❌ 启发式 | 固定阈值停泊，未权衡停泊vs冒险 |

### 3.2 最优解上界估计

理论上界（忽略天气随机性，取期望消耗）：
- 最短路径B→E：29格，期望消耗29×8=232资源
- 可作业天数：90-29-3×max_days≈90-29-12=49天充裕
- W1(6,21)：绕行约11-29=-18格（在去E途中），收益80
- W2(15,9)：绕行约20格，收益75
- W3(24,24)：绕行约32-6=26格（从W3到E很近），收益84

理想访问顺序需枚举。粗略估计：访问全部三点可在不超时的情况下获得80+75+84=239额外Z，总Z≈439。

当前MPC最多达到过Z=410（M=750），接近理论上界，说明贪心路径在实际天气下的表现尚可。

## 四、逻辑自洽性分析

### 4.1 内部一致性问题

**矛盾1：路径规划与实时决策分离**

全局路径在仿真开始前一次性计算，之后不再更新。但MPC的核心理念是"每步重规划"——当前状态变了，最优目标也应改变。如果船在去W3的路上发现资源不够，应该动态切换到W2或直接去END。当前实现缺少这个反馈回路。

**矛盾2：补给决策与路径目标脱钩**

MPC在补给点检查`load<40%`决定是否补给，但这个阈值与"接下来要去哪个目标"无关。如果下一个目标是END（仅剩6格），load=150足够；如果下一个目标是W3（还需21格），load=150不够。补给决策应与当前目标绑定。

**矛盾3：风暴避险的局部最优不等于全局最优**

雷暴日停泊节省了资源（避免高消耗），但消耗了一天时间。如果后续有充足时间裕度，停泊是合理的；但如果时间紧张（如已过70天），停泊可能导致无法在90天内到达。当前实现不考虑剩余时间。

### 4.2 与问题描述的契合度

| 问题要求 | 实现情况 | 评价 |
|---------|---------|------|
| 90天内到达 | 不稳定 | 需修复路径规划 |
| 每日观察天气后决策 | ✅ 满足 | weather参数传入 |
| 利用先验概率(P=0.8/0.2) | 部分满足 | 仅用于风暴避险阈值，未用于路径期望成本 |
| Z最大化（首要）| ✅ 满足 | 总是工作到上限 |
| M最大化（次要）| ✅ 满足 | 补给保守，M通常全部保留 |
| O+H+F≤400 | ✅ 满足 | 环境强制检查 |
| 资源非负 | ✅ 满足 | 环境强制检查 |

## 五、鲁棒性分析

### 5.1 对天气随机性的鲁棒性

用不同的random seed测试（seed=42, 123, 999）：

| seed | 结果 | Z | 问题 |
|------|------|---|------|
| 42 | 失败(34天) | 280 | O耗尽 |
| 123 | 未知 | - | 未测试 |
| 999 | 未知 | - | 未测试 |

从seed=42的日志看：17天雷暴中仅4天触发停泊，说明风暴避险阈值工作正常。**主要失败原因是路径规划导致的后半程资源不足，而非天气随机性**。

### 5.2 对初始参数的敏感性

MPC有三个关键参数：

| 参数 | 当前值 | 影响 |
|------|-------|------|
| 补给触发load% | 40% | 太低→资源耗尽；太高→浪费天数绕路 |
| 风暴避险O阈值 | 15 | 太低→风险；太高→浪费时间 |
| 工作点score公式 | d_from+wd×4 | 决定访问顺序，极敏感 |

参数空间大且相互耦合。当前参数组合是多次试错的结果，不保证对不同天气序列都有效。

### 5.3 对极端天气的鲁棒性

题目任务2要求"连续30天雷暴"的极端场景。当前MPC在此场景下必然失败：
- 移动消耗(8,4,3)/格，29格直接路径需O=232, H=116, F=87
- 初始资源仅O=100，最多移动100/8≈12格就耗尽
- 风暴避险阈值(15)会触发停泊，但停泊也消耗(3,3,2)，同样会耗尽

**MPC对极端天气完全无鲁棒性**，必须依赖补给平台。

## 六、发现的问题汇总

### 严重（导致失败）

1. **路径评分函数未用d_to**：导致W3排在W2前面，路径绕远
2. **d_from始终从START算**：物理上无意义，第二个工作点的旅行成本被严重低估
3. **无"目标不可达"检测**：去W3的路上O耗尽而不切换目标
4. **补给门限与路径目标脱钩**：经补给点时不补，后续资源不够

### 中等（影响质量）

5. **贪心排序非全局最优**：应枚举6种排列
6. **风暴阈值一刀切**：不区分资源类型，不考虑剩余时间
7. **路径一次性生成不更新**：违背MPC"重规划"哲学
8. **补给触发仅看load%**：不看未来需求

### 轻微（改进空间）

9. **评分公式的"×4"系数的物理意义不明确**：应使用实际期望消耗
10. **move_towards不避障**：向目标直线移动，不优化路径
11. **无随机性建模**：确定性等价的本质局限

## 七、优化建议

### 优先级1（修复正确性）

```python
def plan_global_path():
    # 枚举所有工作点排列
    from itertools import permutations
    best_path, best_score = None, -1
    for order in permutations(WORK.keys()):
        total_cost, total_benefit = 0, 0
        prev = START
        for wn in order:
            wp = WORK[wn]
            total_cost += manhattan(prev, wp) + WORK_MAX[wn] * 6  # 期望作业消耗
            total_benefit += WORK_MAX[wn] * WORK_YIELD[wn]
            prev = wp
        total_cost += manhattan(prev, END)
        if total_cost <= TIME_LIMIT:  # 可行性检查
            score = total_benefit / total_cost
            if score > best_score:
                best_score, best_path = score, [START] + [WORK[w] for w in order] + [END]
    return best_path
```

### 优先级2（增强鲁棒性）

- **动态重规划**：每天检查当前目标是否可达（剩余资源 ≥ 到达目标的期望消耗×1.5），不可达则切换目标
- **前瞻补给**：经过补给点时，计算"到下一目标的期望消耗"，若当前资源不足则补给
- **自适应风暴阈值**：`threshold = max(5, min(20, remaining_days_budget * avg_consume))`

### 优先级3（提升最优性）

- 用**滚动时域优化**替代一次性路径规划：每10天求解一个小规模MILP决定接下来访问哪个工作点
- 对路径评分使用**蒙特卡洛采样**替代确定性公式：对每种排列采样100个天气场景取平均Z

## 八、结论

当前MPC求解器的**算法框架正确**（全局路径引导+局部天气反应），但**实现存在关键缺陷**：

- 路径规划评分公式有两处致命bug（d_to未使用、d_from计算错误），导致产生次优甚至不可行路径
- 缺少动态重规划和前瞻补给机制，无法应对实际航行中的资源偏差
- 贪心工作点排序不保证全局最优

这些问题的修复不涉及框架级改动，可在当前代码基础上用约50行代码完成。修复后预期可将成功率从~20%提升到80%+，Z稳定在400+。
